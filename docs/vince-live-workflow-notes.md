# Vince Live Workflow Building — Confirmed Facts

Notes gathered while building the M3 API Catalog Sync workflow (`MRS001MI / LstAllTrans`).
Everything here was confirmed via real execution, a real GET/export, or a real builder-UI test — not inferred from documentation or guessed by analogy. Where something is still open, it's marked as such.

---

## 1. M3 API step output binding

Reference an M3 API step's result directly by step id — the array itself, with **no `.body` or `.data` sub-property**:

```
$context.data.all.<stepId>
```

This differs from a **REST API** step, whose result is wrapped as `{ headers, body }` — so REST API steps *do* need `.body` to reach the payload. Don't assume the same binding convention applies across step types.

## 2. Transform preview pane vs. real execution

The Transform step's builder-UI preview pane, when you paste sample JSON into its "Input" field, binds that data to **bare `$.<stepId>`** — not `$context`.

Only a real saved/executed workflow resolves `$context.data.all.<stepId>`.

**Practical workflow:** write and test the expression against `$.<stepId>` in the preview pane first, then swap to `$context.data.all.<stepId>` before saving for real execution. Forgetting this swap silently produces a blank/empty result with no error — it isn't a syntax problem, `$context` is just undefined in that pane.

## 3. Runtime field naming convention

For a transaction with instance id `<id>` inside an M3 API step:

- A declared **output** field `X` appears at runtime as `<id>_X`
- If `X` is *also* an input field on the same transaction, its **input echo** appears as `<id>_I_X`

Example, for instance id `xu3EO2azWPT` and field `TRNM` (used as both input and output):

```
"xu3EO2azWPT_I_TRNM": "*",        // input echo
"xu3EO2azWPT_TRNM": "LstClaimDet" // declared output value
```

Auto-injected columns also appear per row, even when not declared in `output`:
- `<id>_MSG_COL` — per-row status/error message (e.g. `"OK"`, or a real error string)
- `<id>_<id>_<programName>_<transactionName>_ROWNUM` — observed always `null` in testing; purpose/behavior not otherwise investigated

## 4. Instance ids are not stable

The transaction instance id (e.g. `xu3EO2azWPT`) is **regenerated by Vince Live**, not preserved from whatever you send when creating/updating a workflow via the API. This was confirmed to change:
- Every time a workflow is recreated via `POST /workflows`
- Apparently also across ordinary re-saves of an existing workflow (observed across several iterations of the same workflow in this project)

**Implication:** a Transform template that hardcodes a specific instance id (e.g. `xu3EO2azWPT_TRNM`) will silently break the next time the workflow is saved/recreated, since the real prefix will have changed. Two options:
- Re-edit the Transform template after every save, reading the new instance id back via GET, **or**
- Use dynamic key-matching (see §6) so the template doesn't depend on a fixed instance id at all

## 5. `maxRows`

- `maxRows: 0` means **unlimited**, not zero rows. Confirmed via a real run returning 24,154 records with `maxRows: 0` set (vs. an earlier run capped at exactly 100 records before this was configured).
- Configurable per-transaction directly in the builder UI (transaction settings, not a workflow-level setting).

## 6. Dynamic field matching (for when instance ids can't be hardcoded)

Working pattern to find a field by suffix rather than by hardcoded instance-id prefix, using only standard JSONata functions (`$keys`, `$filter`, `$substring`, `$lookup`) — confirmed working in this Transform engine:

```jsonata
$context.data.all.m3_api_1[$exists($lookup($, $filter($keys($), function($k){$substring($k, -7) = "_I_TRNM"})[0]))].{
  "Program": $lookup($, $filter($keys($), function($k){$substring($k, -5) = "_MINM"})[0]),
  "Transaction": $lookup($, $filter($keys($), function($k){$substring($k, -5) = "_TRNM" and $substring($k, -7) != "_I_TRNM"})[0]),
  "Description": $lookup($, $filter($keys($), function($k){$substring($k, -5) = "_TRDS"})[0]),
  "Type": $lookup($, $filter($keys($), function($k){$substring($k, -5) = "_SIMU"})[0]),
  "Status": $lookup($, $filter($keys($), function($k){$substring($k, -5) = "_STAT"})[0])
}
```

**Design notes:**
- `$substring($k, -N)` extracts the last N characters of a key name; match this against the known field-name suffix (e.g. `_MINM`, 5 chars). Get the character count right — a wrong count silently returns no match, no error, just an empty result. This bit us once during development.
- Row-filtering uses the **input echo** field (`_I_TRNM`), not an output field, to reliably distinguish real data rows from padding/incomplete rows returned by the M3 API step (see §7). `_I_TRNM` is 7 characters, not 6 — the actual field name search string includes both underscores (`_I_TRNM`).
- When two fields share a common suffix (here, `_TRNM` and `_I_TRNM` both end in `_TRNM`), add an explicit exclusion (`and $substring($k, -7) != "_I_TRNM"`) to disambiguate — otherwise the match is ambiguous and may pick either key.

## 7. Known syntax limitation in the Transform editor

Multi-statement, semicolon-chained variable-binding blocks — standard, valid JSONata — **fail to parse** in this specific Transform editor:

```jsonata
( $rows := ...; $findKey := function(...){...}; $rows[...] )
```
→ `Expected "}", got ";"`

This is a limitation of this Transform editor/engine specifically, not of JSONata as a language. Avoid this construct here; use a single nested expression instead (as in §6), even though it's more verbose and repeats `$lookup(...$filter(...))` for each field rather than binding it once.

> **⚠️ THIS NOTE IS NOW IN DOUBT — do not treat it as a constraint without re-testing.**
> Four real production customer workflows (
> "Claim register", "Package Lost", "Display customer credit notes",
> "INT - WHR - Search & return customer order lines") use exactly this construct
> in their Transform steps and work:
> ```jsonata
> (
>   $data := $context.data.trigger.body[0];
>   { "payload": { "program": "OIS100MI", "transactions": $data.{ ... }[] } }
> )
> ```
> So either the failure recorded above had a different cause (a stray brace, or
> the specific expression rather than the construct), or the editor changed
> between then and now. The reference JSONata implementation parses the same form
> without complaint. Re-test before working around it — the workaround costs real
> legibility. See `docs/vince-generic-m3-pipeline.md`.

**Confirmed working in this engine:** `$keys()`, `$substring()`, `$filter()`, `$lookup()`, and inline `function($k){...}` definitions used directly inside an expression (just not bound via `:=` in a semicolon-chained block).

## 8. Padding/incomplete rows in M3 API output

Large M3 API step results have been observed to include rows where every declared output field is `null` — likely padding, or artifacts of how the underlying M3 call paginates/completes. Filtering by the mandatory **input echo field** (`_I_<fieldName>`) reliably excludes these; filtering by an output field does not, since those output fields are exactly what's `null` on the malformed rows.

## 9. Pagination

M3 API steps appear to have built-in, automatic pagination at the workflow-engine level — observed via the compiled AWS Step Functions state machine (`definitionAsl`, returned alongside a workflow's `GET` response), which contains a `CheckForPendingApi` choice state that loops back into the M3 API step whenever `hasPendingSteps = true` or `partialCursor != null`, before continuing to the next step. This suggests manual pagination handling (e.g. building a `forEach`/cursor loop yourself) usually isn't necessary — the engine already loops until the underlying M3 call reports completion. **This is inferred from internal implementation details that could change without notice, not a documented/stable contract** — worth re-verifying if it ever appears to stop working.

## 10. Result payload size — inline vs. file-based

Execution results appear inline in the execution log response (small results) or as a separate `dataFileKey` reference (e.g. `WFEXEC-<id>/dataFile.json`) once the payload crosses some size threshold — observed at 24,154 records. The Workflow API's `GET /live/worfklows/{workflowId}/download-url` endpoint is documented as returning a download URL and was used successfully to retrieve one of these files.
